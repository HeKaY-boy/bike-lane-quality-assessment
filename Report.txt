# Abstract

The quality of bicycle lanes has a direct influence on cycling comfort and road safety. Conventional inspection methods require manual observation and can be time-consuming when applied to extensive cycling networks. This project investigates the use of smartphone sensor data and machine learning to distinguish between smooth and bumpy bicycle lanes.

Accelerometer, gyroscope, and gravity sensor readings are collected while cycling on different surfaces. The recorded time-series data are prepared for analysis, divided into overlapping windows, and transformed into statistical features. Supervised classification and unsupervised clustering methods are then applied to identify patterns associated with road-surface conditions.

The supervised approach learns from labelled smooth and bumpy recordings, whereas unsupervised methods investigate the natural grouping of sensor observations without directly using their class labels during clustering. Model evaluation, dimensionality reduction, and visualization are used to compare the approaches. Finally, the selected model is applied to an independent external dataset to investigate its performance on previously unseen recordings.

The project demonstrates a potential data-driven approach to bicycle-lane assessment. However, the reliability of the resulting classifications depends on sensor placement, recording consistency, feature selection, model generalization, and the representativeness of the collected data.

**Keywords:** Bicycle-lane quality, smartphone sensors, accelerometer, gyroscope, gravity sensor, feature engineering, Random Forest, Gaussian Mixture Model, PCA, clustering, machine learning.

# 1. Business and Objective Understanding

## 1.1 Problem definition

Bicycle lanes can contain surface irregularities such as cracks, potholes, uneven paving, and bumps. These irregularities can reduce cycling comfort and potentially increase the risk of loss of control or accidents.

Manual inspection is useful but can be expensive and difficult to scale across an extensive urban road network. Smartphones provide an alternative source of information because they contain motion sensors capable of recording the movement and orientation of a cyclist and the bicycle.

The central problem addressed in this project is:

**Can smartphone sensor measurements be used to distinguish smooth bicycle-lane sections from bumpy sections using data analysis and machine learning?**

The project considers two approaches:

* **Supervised learning:** Models are trained using sensor windows labelled as smooth or bumpy.
* **Unsupervised learning:** Clustering algorithms are used to identify groups of sensor windows with similar characteristics.

The objective is not to replace professional road inspections but to investigate whether smartphone measurements can support preliminary identification of potentially problematic bicycle-lane sections.

## 1.2 Project objectives

The main objectives are:

1. Understand the structure and quality of the collected sensor data.
2. Combine the measurements from multiple smartphone sensors.
3. Inspect the recordings for missing data, timestamp problems, duplicate observations, and inconsistent sampling.
4. Convert raw time-series measurements into meaningful statistical features.
5. Apply feature selection or dimensionality reduction where appropriate.
6. Train and evaluate supervised classification models.
7. Apply and evaluate unsupervised clustering algorithms.
8. Compare the models using suitable evaluation metrics.
9. Select a model based on performance, suitability, and deployment requirements.
10. Apply the finalized pipeline to the independent external dataset.
11. Visualize the predicted quality of individual sensor windows.

## 1.3 Relevance and potential users

The potential users of a future bicycle-lane monitoring system include municipal road-maintenance teams, urban planners, cycling infrastructure researchers, and cycling advocacy organizations.

Aggregated observations could help prioritize locations for further inspection. However, sensor-based predictions should be treated as indicators of possible surface irregularities rather than definitive engineering assessments.

# 2. Data Understanding

## 2.1 Data collection methodology

The assignment uses smartphone sensor data collected while participants cycle over smooth and bumpy bicycle-lane surfaces. The Sensor Logger application records three sensor types:

| Sensor         | Measurements               | Purpose                                                                               |
| -------------- | -------------------------- | ------------------------------------------------------------------------------------- |
| Accelerometer  | X, Y, Z acceleration       | Captures changes in linear acceleration caused by movement and surface irregularities |
| Gyroscope      | X, Y, Z angular velocity   | Captures rotational movement and changes in device orientation                        |
| Gravity sensor | X, Y, Z gravity components | Provides information about the device's orientation relative to gravity               |

The assignment specifies a default sampling frequency of approximately 100 Hz and recommends consistent smartphone placement and standardized recording conditions. These measures help reduce variation caused by the recording setup rather than the road surface.

The collected recordings are organized into smooth and bumpy categories. Each sensor recording contains timestamps and measurements along three spatial axes.

## 2.2 Dataset structure

The raw accelerometer recordings contain columns such as:

* `time`
* `seconds_elapsed`
* `x`
* `y`
* `z`

Equivalent measurement columns are present in the gyroscope and gravity files.

During preprocessing, the sensor-specific columns are renamed to avoid ambiguity. For example, accelerometer measurements become `acc_x`, `acc_y`, and `acc_z`, while the gyroscope and gravity measurements receive corresponding prefixes.

This naming convention makes it easier to combine the sensor data and identify the origin of each measurement.

The local bike-lane dataset was also inspected using its separate smooth and bumpy directories. A previously examined accelerometer dataset contained 18,456 rows and the five columns `time`, `seconds_elapsed`, `z`, `y`, and `x`, with no missing values reported in that inspection. These figures describe that particular file and should not be interpreted as the total number of observations across all recordings.

## 2.3 Exploratory data analysis

Exploratory data analysis (EDA) is used to understand the measurements before model training.

The following aspects are relevant to this project:

**Signal distributions:** The X, Y, and Z measurements can be plotted over time to examine fluctuations, abrupt changes, and differences between smooth and bumpy recordings.

**Sensor magnitudes:** The magnitude of a three-dimensional sensor signal summarizes its overall intensity without depending on one individual axis.

**Recording duration:** The elapsed timestamps can be used to calculate how long each recording lasted.

**Sampling frequency:** The difference between consecutive timestamps indicates whether the effective sampling frequency is close to the expected 100 Hz.

**Data quality:** Missing values, duplicate timestamps, recording lengths, and timestamp alignment should be checked before merging sensor files.

**Window-level patterns:** Comparing features extracted from smooth and bumpy windows helps determine whether the classes exhibit distinguishable signal characteristics.

These analyses are important because machine learning performance depends on both the quality of the measurements and the degree to which the extracted features represent the target distinction.

## 2.4 Data quality assessment

A reusable `load_and_merge()` function was developed to load the three sensor files, rename their measurement columns, and combine them into one DataFrame.

The function checks whether the recordings contain equal numbers of rows and whether the `time` columns align. If the checks fail, it raises an error rather than silently combining potentially inconsistent measurements.

A `recording_quality()` function was also developed to summarize:

* Number of rows in each recording.
* Recording duration in seconds.
* Effective sampling frequency.
* Number of missing values.
* Number of duplicate timestamps.

The results are stored in a quality-summary DataFrame, allowing multiple recordings to be compared systematically.

A separate `signal_summary()` function calculates the standard deviation and maximum of the accelerometer magnitude for each recording. This provides a simple initial comparison of signal variability and intensity.

These summaries are useful for identifying potentially problematic recordings. However, a low standard deviation or high maximum alone cannot conclusively determine whether a bicycle lane is smooth or bumpy.

# 3. Data Preparation

## 3.1 Loading and merging sensor recordings

The accelerometer, gyroscope, and gravity files are loaded independently using pandas. Their measurement columns are renamed before the data are combined.

The `load_and_merge()` function uses the accelerometer timestamps as the reference and attaches the gravity and gyroscope measurements after checking row counts and timestamp alignment.

This approach makes the subsequent processing easier because each timestamp is represented by a single row containing measurements from the three sensors.

**Technical consideration:** Checking only the `time` column and the row count is not sufficient to guarantee complete alignment. A stronger validation should compare both `time` and `seconds_elapsed` across the files. If the files have different timestamp sequences, they should be aligned using an explicitly justified timestamp-matching method rather than relying on row position.

The inner-merge approach used in the earlier deployment code and the row-wise assignment approach in `load_and_merge()` also have different assumptions. The row-wise method is appropriate only when the recordings have already been verified to be aligned.

## 3.2 Missing values and duplicate timestamps

Missing values can affect feature extraction and may cause model predictions to fail. Duplicate timestamps can indicate repeated measurements, although they are not automatically invalid in every recording setup.

The quality checks quantify these issues before further processing.

Where missing values or invalid observations are found, the appropriate response depends on their extent and cause. Options include removing a small number of invalid rows, correcting the source-data issue, or using a justified imputation method. Any such treatment should be documented.

The earlier inspected accelerometer file contained no missing values. Nevertheless, the same checks should be performed on every recording and sensor file, rather than assuming that all files have identical quality.

## 3.3 Sensor magnitude calculation

For each sensor, a magnitude is calculated from the three spatial components:

$$
m(t)=\sqrt{x(t)^2+y(t)^2+z(t)^2}
$$

This produces three derived signals:

* `acc_mag`
* `gyro_mag`
* `grav_mag`

The main advantage is that the magnitude summarizes the overall intensity of the three-dimensional signal. It reduces dependence on a particular axis and can help accommodate changes in device orientation.

However, magnitude calculation also discards directional information. Two different movement patterns may have similar magnitudes even if their individual X, Y, and Z components differ. A future comparison could therefore evaluate whether axis-specific features improve classification.

The gravity magnitude may be relatively stable under normal conditions. Consequently, its statistical features may contribute less discrimination than acceleration-related features. Its actual usefulness should be established through feature analysis and model comparison.

## 3.4 Windowing strategy

The continuous sensor recordings are divided into fixed-size, overlapping windows using the reusable `create_window()` function.

The selected settings are:

| Parameter          |       Value | Explanation                               |
| ------------------ | ----------: | ----------------------------------------- |
| Sampling frequency |      100 Hz | Approximately 100 observations per second |
| Window duration    |   2 seconds | Provides a local segment of the signal    |
| Window size        | 200 samples | \(100 \times 2\) observations             |
| Step duration      |    1 second | Windows start one second apart            |
| Step size          | 100 samples | Half of the window size                   |
| Overlap            |         50% | Adjacent windows share 100 samples        |

For a recording containing \(N\) observations, the number of complete windows is:

$$
n_{\text{windows}}=
\begin{cases}
0, & N<200\\
1+\left\lfloor\frac{N-200}{100}\right\rfloor, & N\geq200
\end{cases}
$$

Overlapping windows increase the number of training examples and provide a more continuous view of changing road conditions.

A two-second window is a practical starting point because it captures short-term sensor fluctuations without requiring a long recording segment. However, the choice is a design decision rather than a proven optimum. Shorter windows may provide better localization, whereas longer windows may provide more stable statistical estimates.

The window settings must remain consistent during training and deployment.

## 3.5 Window visualization

The first few windows are plotted against `seconds_elapsed` to inspect how the signal changes over time.

These plots help verify that:

* Windows contain the expected number of samples.
* The windows overlap as intended.
* The time axis is interpreted correctly.
* Sudden changes in acceleration can be visually inspected.

The visualization code plots `acc_x`, despite a comment referring to the Z-axis. The axis label and plot title should be corrected so that the report accurately describes the displayed signal.

A further improvement is to plot all three acceleration axes or the acceleration magnitude and compare representative smooth and bumpy recordings using the same scale.

# 4. Feature Engineering and Selection

## 4.1 Motivation for feature extraction

Raw sensor recordings are time-series measurements. Feeding every individual observation directly into a conventional tabular model would create a large number of correlated features and make each training example dependent on a particular time sequence.

Feature extraction converts each window into a compact numerical representation. The resulting feature vector summarizes the statistical characteristics of the sensor signals and can be used by both supervised and unsupervised algorithms.

## 4.2 Statistical features

Five statistical features are calculated for each sensor magnitude.

| Feature            | Definition                                | Interpretation                      |
| ------------------ | ----------------------------------------- | ----------------------------------- |
| Mean               | Average magnitude                         | Represents the average signal level |
| Standard deviation | Spread around the mean                    | Represents signal variability       |
| RMS                | Square root of the mean squared magnitude | Represents signal intensity         |
| Minimum            | Smallest magnitude in the window          | Captures the lower observed level   |
| Maximum            | Largest magnitude in the window           | Captures the highest observed level |

For a signal containing \(n\) values \(x_1,\ldots,x_n\), the root mean square is:

$$
\operatorname{RMS}(x)=
\sqrt{\frac{1}{n}\sum_{i=1}^{n}x_i^2}
$$

Standard deviation measures variation within a window. Larger variation may occur when a bicycle travels over an irregular surface, but rider movement, phone placement, and other factors can also increase the variation.

The mean and RMS summarize signal magnitude, while minimum and maximum provide information about its observed range.

## 4.3 Feature set

The feature-extraction implementation creates the following features:

**Accelerometer:** `acc_std`, `acc_mean`, `acc_rms`, `acc_min`, `acc_max`

**Gyroscope:** `gyro_std`, `gyro_mean`, `gyro_rms`, `gyro_min`, `gyro_max`

**Gravity:** `grav_std`, `grav_mean`, `grav_rms`, `grav_min`, `grav_max`

The resulting feature matrix contains 15 columns when all three sensors are included and each window is successfully processed.

This representation substantially reduces the length of each raw window to a small set of descriptive measurements.

## 4.4 Important implementation consistency

A critical requirement is that training and deployment use identical feature definitions.

For example, the standard deviation calculated by NumPy with its default settings uses the population denominator, whereas pandas' default standard deviation uses the sample denominator. These calculations can produce slightly different values. The implementation should therefore use the same convention in both stages.

Feature names, feature order, units, magnitude calculations, window length, and step size must also be consistent.

During deployment, the feature matrix is reordered according to `sc.feature_names_in_` when those feature names are available. Missing expected features raise an error instead of allowing an invalid prediction to proceed.

## 4.5 Feature selection and dimensionality reduction

Feature selection and dimensionality reduction address different problems.

Feature selection identifies which original variables are most useful for distinguishing the classes. Dimensionality reduction transforms the original feature space into a smaller set of new variables.

Principal Component Analysis (PCA) was incorporated into the supervised and external-deployment pipeline. The discussed configuration uses `PCA(n_components=0.95)`, which retains enough principal components to explain approximately 95% of the variance in the data used to fit PCA.

PCA can reduce redundancy among correlated statistical features and produce a more compact representation. It does not, however, guarantee that all information useful for distinguishing smooth and bumpy surfaces is retained, because PCA prioritizes variance rather than class discrimination.

For this project, it is useful to compare the performance of models trained on the original standardized features with models trained on PCA-transformed features.

# 5. Modeling

## 5.1 Modeling strategy

Two complementary modeling strategies are considered.

Supervised learning uses the known labels of the training windows to learn a mapping between sensor features and road-surface categories.

Unsupervised learning groups similar observations without using their labels to form the clusters. The resulting clusters are subsequently compared with the known labels to assess whether the discovered structure corresponds to the smooth/bumpy distinction.

The assignment calls for four supervised and four unsupervised approaches. The final report and notebook should list the exact eight algorithms implemented by the group, together with their configurations and results. The detailed implementation discussed here specifically includes Random Forest, Gaussian Mixture Model, K-Means, Agglomerative Clustering, and Fuzzy C-Means.

## 5.2 Supervised learning

### 5.2.1 Training and validation procedure

The supervised workflow uses a train-test split with a test fraction of 30%, a random seed of 42, and stratification by class.

Stratification helps maintain approximately the same class proportions in the training and test sets.

The intended workflow is:

1. Split the labelled feature matrix into training and test sets.
2. Fit the scaler on the training features.
3. Transform the training and test features using the fitted scaler.
4. Fit PCA on the scaled training features.
5. Transform the training and test features using the fitted PCA.
6. Train each supervised model using the transformed training features.
7. Predict the test-set labels.
8. Calculate evaluation metrics and inspect the confusion matrix.

**Data leakage consideration:** The scaler and PCA must be fitted only on the training data. Fitting either transformation on the entire dataset before splitting would allow information from the test set to influence training.

If several overlapping windows originate from the same recording or participant, a random window-level split can also lead to overly optimistic evaluation because related windows may appear in both sets. A stronger evaluation uses a group-aware split by participant or recording, where the data volume permits it.

## 5.3 Why Random Forest was considered

Random Forest is a supervised ensemble-learning method that combines predictions from multiple decision trees. Each tree is trained using randomized subsets of the training observations and features, and the trees collectively produce a classification decision.

It is a reasonable candidate for this project for several reasons:

* **Nonlinear relationships:** Road-surface conditions may not be separated by simple linear boundaries.
* **Tabular features:** The model naturally works with the statistical features extracted from sensor windows.
* **Robustness:** Combining multiple trees can reduce the instability of a single decision tree.
* **Limited preprocessing requirements:** Random Forest does not inherently require feature standardization, although standardization may be part of the chosen pipeline.
* **Practical inference:** Once trained, the model can classify new windows without retraining.
* **Feature analysis:** Feature importance can provide additional insight when calculated and interpreted carefully.

These are reasons to evaluate Random Forest, not evidence that it is the best model in this particular dataset. The final choice must be supported by the measured test results.

### 5.3.1 Random Forest prediction pipeline

The deployment implementation performs the following operations:

1. Load external accelerometer, gyroscope, and gravity data.
2. Merge the sensor measurements.
3. Calculate sensor magnitudes.
4. Divide the recording into overlapping windows.
5. Extract the statistical features.
6. Apply the previously fitted scaler.
7. Apply the previously fitted PCA transformation.
8. Pass the transformed features to the trained Random Forest.
9. store the predicted class for each window.
10. Summarize the prediction counts and visualize the predictions.

A feature-dimension check is included to verify that the PCA output matches the number of input features expected by the Random Forest model.

This check is important because a model trained on a different feature representation cannot be used reliably with an incompatible deployment matrix.

## 5.4 Unsupervised learning

### 5.4.1 Purpose

Unsupervised methods are included to investigate whether the sensor windows naturally form groups that correspond to smooth and bumpy road conditions.

The clustering methods do not automatically know the meaning of the target categories. For example, cluster 0 is not inherently the smooth class, and cluster 1 is not inherently the bumpy class.

Cluster interpretation must be supported by analysis of the corresponding feature values and comparison with the known labels.

### 5.4.2 K-Means

K-Means partitions the feature space into a specified number of clusters by minimizing the within-cluster sum of squared distances to the cluster centers.

It is computationally efficient and provides a useful baseline for determining whether the feature representation supports separation into two groups.

Its limitations include sensitivity to feature scaling, initialization, outliers, and the geometry of the clusters. K-Means works best when the cluster structure is reasonably compatible with its distance-based objective.

### 5.4.3 Agglomerative Clustering

Agglomerative Clustering builds a hierarchy of clusters by repeatedly combining observations or groups according to a selected linkage criterion.

It can reveal hierarchical structure in the feature space and does not require the assumption that all clusters are spherical.

However, the result can depend on the distance metric, linkage criterion, and chosen number of clusters. It can also be more computationally expensive than K-Means on larger datasets.

A practical implementation issue is that the standard scikit-learn `AgglomerativeClustering` estimator does not provide a normal `predict()` method for previously unseen samples. Consequently, fitting a new clustering model on the external dataset is not equivalent to assigning observations to the clusters learned from the training dataset.

### 5.4.4 Fuzzy C-Means

Fuzzy C-Means allows each observation to have a degree of membership in multiple clusters rather than assigning every observation exclusively to one cluster during the fitting process.

This can be useful when road conditions change gradually or when a window contains a mixture of smooth and irregular surface behavior.

The membership values express similarity to the clusters; they should not automatically be interpreted as calibrated probabilities that a road section is smooth or bumpy.

The final cluster assignment depends on the membership values and the chosen decision rule.

### 5.4.5 Gaussian Mixture Model

A Gaussian Mixture Model (GMM) represents the data as a mixture of Gaussian probability distributions. It estimates the parameters of the component distributions and assigns each observation a probability of belonging to each component.

GMM was considered because it can model clusters with different shapes and spreads, depending on the covariance configuration. It also provides soft membership probabilities in addition to the most likely cluster assignment.

This is useful when the boundary between smooth and bumpy windows is not perfectly clear.

GMM nevertheless makes distributional assumptions that may not accurately represent every sensor dataset. It can also converge to local solutions and is sensitive to initialization and component configuration.

For this project, GMM is particularly useful as a comparison with distance-based methods such as K-Means. The final report should specify the number of mixture components, covariance type, initialization, and random seed used.

### 5.4.6 Comparison of supervised and unsupervised methods

| Consideration              | Supervised learning                            | Unsupervised learning                                                  |
| -------------------------- | ---------------------------------------------- | ---------------------------------------------------------------------- |
| Uses labels during fitting | Yes                                            | No                                                                     |
| Main purpose               | Predict known road-surface categories          | Discover structure in sensor features                                  |
| Output                     | Predicted class                                | Cluster assignment or membership                                       |
| Evaluation                 | Accuracy, precision, recall, F1-score          | ARI, NMI, silhouette score                                             |
| Main advantage             | Directly learns the target distinction         | Can reveal structure without relying on labels                         |
| Main limitation            | Requires reliable labels                       | Clusters may not correspond to the target classes                      |
| External deployment        | Straightforward with a fitted prediction model | Depends on whether the algorithm supports assignment of unseen samples |

The two approaches answer related but different questions. A supervised model is the more direct choice when the operational objective is to classify new observations into predefined smooth and bumpy categories.

# 6. Model Evaluation

## 6.1 Supervised evaluation metrics

The supervised models are evaluated on held-out test data. The selected metrics should capture both overall correctness and the ability to detect bumpy road sections.

### Accuracy

Accuracy measures the fraction of predictions that match the true labels:

$$
\text{Accuracy}=\frac{TP+TN}{TP+TN+FP+FN}
$$

Accuracy is easy to understand, but it can be misleading if the classes are imbalanced.

### Precision

Precision measures the fraction of predicted bumpy windows that are actually bumpy:

$$
\text{Precision}=\frac{TP}{TP+FP}
$$

High precision reduces false alarms, where a smooth section is incorrectly identified as bumpy.

### Recall

Recall measures the fraction of actual bumpy windows that are detected:

$$
\text{Recall}=\frac{TP}{TP+FN}
$$

High recall is important when the objective is to identify potentially problematic road sections. A false negative occurs when a bumpy window is classified as smooth.

### F1-score

The F1-score combines precision and recall using their harmonic mean:

$$
F_1=2\frac{\text{Precision}\cdot\text{Recall}}
{\text{Precision}+\text{Recall}}
$$

For consistent interpretation, the positive class should be defined as `bumpy` when calculating the binary precision, recall, and F1-score.

## 6.2 Confusion matrix

A confusion matrix compares the actual class against the predicted class. The matrix should explicitly use the order `bumpy`, `smooth` so that the positions of the values are unambiguous.

The matrix helps distinguish between:

* True positives: Bumpy windows correctly identified.
* True negatives: Smooth windows correctly identified.
* False positives: Smooth windows incorrectly classified as bumpy.
* False negatives: Bumpy windows incorrectly classified as smooth.

The last error type is especially relevant to the project's intended use because undetected surface irregularities may be more consequential than unnecessary inspection alerts.

## 6.3 Unsupervised evaluation metrics

The clustering models are evaluated using three complementary measures.

**Adjusted Rand Index (ARI):** Measures agreement between cluster assignments and true labels while correcting for agreement expected by chance. A value near 1 indicates strong agreement, while a value near 0 indicates agreement comparable to chance under the metric's reference.

**Normalized Mutual Information (NMI):** Measures the shared information between the clustering assignments and the true labels. Higher values indicate greater correspondence between the discovered clusters and the labelled classes.

**Silhouette Score:** Measures how similar each observation is to its own cluster compared with other clusters. Higher values generally indicate better separation in the feature space. It does not measure agreement with the true labels.

ARI and NMI are suitable for comparing clusters against known labels because they are invariant to cluster-ID permutations. For example, swapping the names of clusters 0 and 1 does not change the agreement score.

The silhouette score should be calculated on a clearly specified feature representation and the corresponding cluster assignments. If PCA features are used, this should be stated in the results.

## 6.4 Evaluation limitations

A conventional held-out test set is straightforward for supervised prediction models. Clustering algorithms require additional care.

For example, fitting Agglomerative Clustering independently on the test set and comparing the resulting clusters with test labels measures the structure found within the test set. It does not measure the ability of a model fitted on training data to assign unseen observations to previously learned clusters.

Similarly, mapping cluster IDs to smooth or bumpy based on the test labels and then reporting performance on those same labels would introduce information leakage.

For a fair comparison, cluster interpretation should be based on training data or on a separate validation procedure. Where an algorithm does not support prediction for new observations, its deployment limitations should be stated explicitly.

# 7. Obstacles, Debugging, and Technical Observations

Several implementation details required particular attention during development.

## 7.1 Sensor alignment and data merging

The three sensors produce separate recordings. Combining them without checking timestamps could associate measurements from different moments.

The reusable loading function addresses this by checking the row counts and timestamp alignment before combining the data.

**Lesson learned:** Sensor fusion requires synchronization, not merely placing columns next to one another. Future versions should verify both timestamp columns and document any tolerance used for alignment.

## 7.2 Feature dimension mismatch

During deployment, the external feature matrix contained statistical features derived from three sensors. However, the trained model and fitted transformations may have been built using a different set of features.

This creates a mismatch between the feature matrix and the scaler or PCA transformation.

The implementation was improved by checking the expected feature names, restoring their training order, and raising an error when features are missing. It also checks that the number of PCA components matches the Random Forest input dimension.

**Lesson learned:** A trained model is only compatible with the feature representation on which it was fitted. Adding gravity features at deployment requires retraining the relevant pipeline if those features were not included during training.

## 7.3 Window creation and sampling assumptions

The project uses a window size of 200 and a step size of 100, based on the intended 100 Hz sampling frequency.

If the actual sampling frequency differs substantially from 100 Hz, a window of 200 observations may no longer represent two seconds. Uneven sampling can also affect the meaning of statistical features.

The recording-quality summary provides an initial way to check the effective frequency.

**Lesson learned:** Window sizes should be defined in relation to the sampling frequency, and irregular recordings should be investigated before feature extraction.

## 7.4 DataFrame shape and column assignment

A pandas error occurred during an assignment involving a DataFrame and a target-label variable. Such errors can arise when the assigned values have a different length from the number of rows, or when the labels do not correspond to the current train-test split.

The appropriate correction is to ensure that the label vector and feature matrix refer to the same observations and have compatible lengths.

**Lesson learned:** After splitting or transforming data, explicitly check the shapes and alignment of feature matrices and labels before assigning columns or fitting models.

## 7.5 Clustering metrics and model comparison

The unsupervised evaluation workflow required distinguishing between classification metrics and clustering metrics.

Accuracy, precision, recall, and F1-score directly assess predicted class labels. ARI and NMI evaluate agreement between clusters and known labels, while the silhouette score evaluates cluster separation.

The resulting metrics should not be interpreted as interchangeable.

**Lesson learned:** Metrics must be selected according to the modeling task. A high silhouette score does not necessarily mean that the clusters accurately distinguish smooth from bumpy road conditions.

## 7.6 PCA visualization

PCA was used to reduce the feature representation and visualize the data in two dimensions. The first two components provide a convenient projection, but they do not necessarily capture all class-discriminative information.

A visualization showing overlapping classes does not automatically mean that a classifier cannot separate them in the full feature space. Conversely, apparent visual separation does not guarantee good generalization.

**Lesson learned:** Visualizations support interpretation, but numerical evaluation on held-out data remains necessary.

## 7.7 Deployment compatibility

The deployment code reuses the trained scaler, PCA transformation, and Random Forest model instead of fitting new transformations on the external data.

This preserves the representation learned during training. The external dataset is processed only after the modeling and model-selection steps have been completed.

**Lesson learned:** Reproducible deployment requires preserving the entire preprocessing pipeline, not just the final estimator.

# 8. Model Selection and Justification

## 8.1 Recommended selection approach

The preferred model should be selected based on the actual results rather than on the algorithm's popularity or complexity.

The selection process should consider:

1. Held-out predictive performance.
2. Recall for the bumpy class.
3. Precision and F1-score.
4. Consistency across recordings or participants.
5. Computational cost and inference time.
6. Compatibility with the deployment pipeline.
7. Interpretability and maintainability.

Random Forest is a strong candidate because the project uses a compact tabular feature representation and the target consists of two predefined classes. It can model nonlinear relationships and can be applied directly to previously unseen feature vectors after training.

However, it should be selected as the final model only if the results support that choice. A simpler model may be preferable if it achieves comparable performance with fewer computational or maintenance requirements.

## 8.2 Supervised versus unsupervised selection

For the final operational objective—assigning a smooth or bumpy label to a new window—a supervised model is generally more directly suitable because it is trained using the desired target categories.

Unsupervised learning remains valuable for exploratory analysis, discovering possible subgroups, and checking whether the engineered features contain a natural grouping related to road quality.

The final report should state which supervised model was selected, why its results were preferred, and what the unsupervised analysis revealed. Those conclusions must be based on the executed results rather than assumed in advance.

# 9. Deployment on the Independent External Dataset

## 9.1 Purpose of external deployment

After the training and evaluation stages, the finalized pipeline is applied to the independent external sensor recordings.

The external dataset must not be used to fit the models, select hyperparameters, or decide which model performs best. Its purpose is to assess how the finalized system behaves on previously unseen recordings.

This separation is important because good performance on the original test data does not guarantee successful generalization to new recording conditions.

## 9.2 Deployment workflow

The implemented workflow consists of the following stages:

1. Load the external accelerometer, gyroscope, and gravity CSV files.
2. Validate the recordings and merge the sensor measurements.
3. Calculate the magnitude of each sensor's three-dimensional measurements.
4. Divide the recording into 200-sample windows with a 100-sample step.
5. Extract the statistical features for every complete window.
6. Verify feature compatibility and reorder columns to match training.
7. Apply the previously fitted scaler.
8. Apply the previously fitted PCA transformation.
9. Use the trained Random Forest model to classify each window.
10. Store the predicted class alongside the window number.
11. Summarize the predicted class counts.
12. Visualize the predictions using the first two PCA components.

The same feature-extraction and preprocessing functions are reused for GMM deployment. The principal difference is the final prediction step.

## 9.3 Random Forest deployment

Random Forest produces a predicted class for each external window. The results are stored in a table containing the window number and predicted class.

Counting the predictions gives an initial summary of how many windows were classified as smooth and how many were classified as bumpy.

The PCA scatter plot provides a visual representation of the external windows, with points grouped by predicted class.

This plot is useful for inspecting the distribution of predictions, but it is not a map of the physical road and does not independently verify whether the predictions are correct.

## 9.4 GMM deployment

GMM produces a cluster assignment for each external window and can also return the membership probabilities for its mixture components.

The probability columns describe the estimated membership of a window in each Gaussian component. They should not be presented as calibrated probabilities of a smooth or bumpy label without a separate validation procedure.

Unlike Random Forest, GMM does not inherently assign semantic class names to its components. Cluster identities must be interpreted using training data or another justified analysis.

## 9.5 Practical deployment considerations

A future operational implementation could process sensor data continuously and aggregate predictions into road segments.

However, the current window-level deployment does not automatically establish the geographic location of each road segment. A physical road-quality map would require location information, appropriate privacy safeguards, and a method to associate each prediction with a geographic position.

A practical system should also consider:

* Missing or interrupted sensor recordings.
* Changes in phone orientation or placement.
* Different bicycles, riders, speeds, and phone models.
* Variation in road materials and environmental conditions.
* Uncertainty near transitions between smooth and bumpy surfaces.
* False alarms and missed detections.
* Storage, privacy, and data-retention requirements.

Predictions should be aggregated over nearby windows carefully. For example, a short run of isolated bumpy predictions might be treated differently from a sustained sequence of bumpy predictions, provided the aggregation rule is validated.

# 10. Limitations and Future Improvements

## 10.1 Data collection limitations

The measured sensor signals are influenced by more than road quality. Bicycle speed, rider movement, phone placement, bicycle suspension, and recording-device characteristics can all affect the measurements.

If the dataset contains only a small number of participants or locations, the learned patterns may not generalize to different riders and roads.

Future data collection should include more participants, multiple bicycles, different phone models, varied road surfaces, and repeated recordings under standardized conditions.

## 10.2 Window-level labels

Assigning a single label to a complete window assumes that the window represents one road-surface condition.

A window spanning a transition from smooth to bumpy pavement may contain both conditions. Such mixed windows can introduce label noise, particularly near road-surface boundaries.

Future work could examine shorter windows, transition labels, or a validated aggregation strategy that better reflects the spatial continuity of road conditions.

## 10.3 Feature limitations

The statistical features summarize the magnitude distributions but do not fully describe signal frequency content or directional patterns.

Potential future features include:

* Axis-specific statistical features.
* Signal energy and peak-to-peak amplitude.
* Frequency-domain characteristics, if permitted by the course methods.
* Additional temporal features that capture abrupt changes.
* Feature importance and feature-selection analysis.

These alternatives should be evaluated experimentally rather than added without evidence.

## 10.4 Generalization and validation

A random train-test split may place overlapping windows from the same recording in both sets. Because those windows share many observations, the evaluation may overestimate the model's ability to generalize to new participants or locations.

A stronger evaluation would separate entire recordings or participants between training and testing. This would provide a more realistic indication of performance on unseen cycling conditions.

The independent external dataset should remain untouched until the model and its settings have been finalized.

## 10.5 Model and deployment limitations

Random Forest provides direct class predictions but does not automatically indicate the physical location or severity of a road defect.

GMM and other clustering methods can identify groups in feature space, but the groups may reflect differences in phone movement or recording conditions instead of road quality.

PCA also introduces a trade-off between reducing dimensionality and preserving useful information.

Future work should compare pipelines with and without PCA, assess feature importance, calibrate prediction confidence where appropriate, and measure inference time on a target device.

## 10.6 Recommendations

The following improvements are recommended:

1. Standardize phone placement and document recording conditions.
2. Validate timestamp alignment across all sensor files.
3. Check sampling frequency and missing data for every recording.
4. Keep the training and deployment feature pipelines identical.
5. Use participant- or recording-level validation where feasible.
6. Report confusion matrices and class-specific recall.
7. Compare supervised and unsupervised methods using appropriate metrics.
8. Analyze false positives and false negatives to identify systematic errors.
9. Use external deployment only after finalizing the model.
10. Add GPS-based mapping and spatial aggregation only when reliable location data are available and privacy requirements are satisfied.

# 11. Ethical and Privacy Considerations

The assignment involves recordings from consenting adult participants. Sensor data should be used only for the educational purpose described in the project.

Recordings should be organized and anonymized appropriately, and any location information added in future work should receive particular care because it can reveal travel patterns.

The data-collection procedure should prioritize participant safety. Cycling trials should be conducted on appropriate routes, and participants should stop if they experience discomfort or unsafe conditions.

Any future system should communicate that its predictions are automated estimates requiring validation, rather than definitive evidence of a road defect.

# 12. Conclusion

This project investigates the feasibility of using smartphone motion sensors to assess bicycle-lane quality. The workflow covers sensor-data loading, quality checks, multi-sensor merging, magnitude calculation, windowing, statistical feature extraction, model training, evaluation, and deployment on an independent external dataset.

The preprocessing pipeline transforms continuous measurements from the accelerometer, gyroscope, and gravity sensors into fixed-length feature vectors. A two-second window and one-second step provide overlapping observations that can be analyzed by both supervised and unsupervised methods.

Random Forest is a suitable candidate for the supervised classification task because it can learn nonlinear relationships between the extracted features and the smooth/bumpy labels. Gaussian Mixture Model, K-Means, Agglomerative Clustering, and Fuzzy C-Means provide complementary ways to investigate the structure of the feature space.

The implementation work also highlights several important practical lessons: sensor synchronization must be verified, training and deployment features must match exactly, preprocessing transformations must be reused consistently, and evaluation metrics must reflect the modeling objective.

The final model selection must be supported by the actual evaluation results. Similarly, successful execution of the external prediction pipeline demonstrates technical compatibility, but does not by itself establish the real-world accuracy of the predictions.

Overall, smartphone-based bicycle-lane monitoring offers a promising direction for scalable infrastructure assessment. Further data collection, stronger validation, systematic error analysis, and geographic aggregation would be needed before the approach could be relied upon for real-world maintenance decisions.
